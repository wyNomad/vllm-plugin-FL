# 16k 长输入基线：第一步离线日志分析

本报告只分析 2026-10-07 至 10-08 已归档的原版基线，没有启动服务器、修改参赛源码或重跑测试。原始数据见 `../baseline_20261007/`。`analyze_baseline.py` 从服务日志抽取约每 10 秒一次的 Engine 指标，连续两次空闲采样作为轮次分界；与原始 CSV 的八轮顺序逐一对应，结果在 `engine_run_summary.csv`。各轮日志分段时长与基准耗时基本一致；采样统计不是逐请求计时。

## 关键证据

| 指标 | 4k 正式轮次 2–4 | 16k 正式轮次 2–4 |
| --- | ---: | ---: |
| 每轮请求数 / 配置并发 | 256 / 64 | 128 / 64 |
| 平均 Total tok/s | 1977.17 | 918.04 |
| 平均 TTFT | 11.62 秒 | 598.12 秒 |
| 平均 TPOT | 148.55 毫秒 | 486.02 毫秒 |
| Engine 实际最高 Running | 64 | 31 |
| Engine Running 中位数 | 64 | 30 |
| Engine Waiting 中位数 | 0 | 34 |
| 有请求等待的日志采样占比 | 约 17%–18% | 每轮 97.1% |
| KV 占用至少 90% 的采样占比 | 0% | 每轮 81.7% |
| KV 占用至少 95% 的采样占比 | 0% | 每轮 51.0%–53.1% |
| KV 占用最高值 | 61.6%–61.9% | 99.7%–99.9% |

引擎启动日志报告 GPU KV Cache 容量 **523,056 token**。按提示词与最大输出长度粗算，64 路 4k 请求为 `64 × (4096 + 1024) = 327,680 token`，约为缓存的 62.6%，与日志约 62% 的峰值相符。64 路 16k 请求仅提示词就需 `64 × 16384 = 1,048,576 token`，约为容量的两倍；若每路保留全部 1024 个输出 token，30 路约需 `30 × (16384 + 1024) = 522,240 token`，接近缓存上限。这与日志中最多约 31 个 Running、长期排队和 KV 高占用相吻合。这里是容量量级估算，不等同于逐请求的实际 KV 分配轨迹。

**判断：16k 已明显受到 KV 容量与排队约束。**不过现有日志尚不能把 598 秒 TTFT 精确拆成“排队时间”和“预填充计算时间”，也不能断言容量是吞吐下降的唯一原因。按基准 CSV 的输入 token、输出 token 和耗时计算，16k 正式轮次的有效输入处理率约 **864 token/s**、输出约 **54 token/s**；4k 则约 **1581 token/s**、输出约 **395 token/s**。长上下文内核成本、调度及解码速度仍需要下一步实验区分。日志中没有逐请求的入队、调度、首次输出时间戳；未发现明确的 preemption 记录，也不能据此证明没有发生预抢占。

## 下一步要验证的两个问题

1. 相同 16k 输入在低并发时的 TTFT 和预填充耗时是多少？若低并发也慢，应进一步定位长上下文算子。
2. 并发从低于约 30 提高到 64 时，排队时间与吞吐如何变化？需要采集请求阶段指标或轻量时间戳，确认 KV 容量约束对 TTFT 的贡献。

这些诊断测试使用独立记录，不改变赛事正式服务参数、原版 benchmark 脚本或已有基线结果。
