# 16k 短输出分阶段诊断（修正版）

2026-10-08 在天数 BI-V150 GPU 0 上，使用与赛题一致的 MiniCPM5-2B 服务参数及未改动的参赛源码，独立运行五组**诊断**请求。输入长度 16384，输出长度 1；并发和请求数同为 1、16、32、64。各组使用不同随机种子，服务端记录的前缀缓存命中 token 均为 0，预抢占均为 0。首次单请求用于预热。全部请求成功，脚本退出码 0，个人一次性容器已自动停止。

| 组别 | 平均 TTFT | 平均排队 | 平均预填充 | 采样最高 Running | 采样最高 KV 占用 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 单请求预热 | 27.14 s | 约 0 s | 26.99 s | 1 | 2.74% |
| 单请求复测 | 13.87 s | 约 0 s | 13.75 s | 1 | 3.13% |
| 16 并发 | 116.76 s | 100.03 s | 15.81 s | 1 | 3.13% |
| 32 并发 | 226.33 s | 209.17 s | 15.84 s | 1 | 3.13% |
| 64 并发 | 445.50 s | 426.51 s | 15.89 s | 1 | 3.13% |

数据来自 vLLM `/metrics` 的各请求阶段直方图在每组开始和结束之间的增量；Running、KV 是约每 10 秒的采样，可能错过短暂峰值。客户端 benchmark 的 32 并发平均 TTFT 为 226.49 s，与服务端的 226.33 s 接近。原件见 `phase_summary.json`、`metrics_samples.csv` 和各组 `.log`；服务日志见 `serve_diag_16k_20261008_v2.log`。

**结论：短输出的长输入测试主要慢在排队，且这不是 KV 容量不足引起的。**16 并发下平均 TTFT 的约 86% 是 WAITING 时间，64 并发下约 96%；预填充单请求耗时维持在约 16 秒，而 KV 占用从未超过约 3.13%。每个采样点最多只看到 1 个 Running 请求。当前镜像的 vLLM 0.24.0 源码在 32 GB 卡、API 服务、默认 balanced 模式下把每轮 `max_num_batched_tokens` 推导为 2048；V1 调度器先为 Running 请求分配 token 预算，再处理 Waiting。16k 输入要分多轮预填充，这与观测到的串行推进一致。**2048 是按源码默认逻辑推导，并非直接读取运行时配置字段。**

这组是预填充隔离实验，**不是赛题的 `[16384,1024,64,128]` 评分负载**。正式负载中输出更长，解码会与预填充竞争，KV 使用率在原基线日志中也曾接近 100%；不能把本表的阶段占比直接套到正式成绩。下一步应在同负载的一轮诊断中采集相同指标，再决定是否对预填充内核或调度逻辑做代码优化。提高服务 CLI 的批处理 token 参数不能作为最终参赛优化，因为赛题要求服务参数与基线一致。
