## 本地核验

在仓库根目录运行：

```bash
python3 experiments/iluvatar/results/native2d_20261011/analyze_formal.py
cd experiments/iluvatar
sha256sum -c SHA256SUMS.txt --quiet
```

Native 2D 对容器内安装的 vLLM 0.24 打补丁。可在原固定镜像的一次性容器内先运行 `patch_vllm.py --dry-run` 核验源码，只有哈希和补丁锚点匹配才应用补丁。第一版用 `VLLM_FL_NATIVE2D_PROBE=1` 开关；下一版用独立开关，尚未验证。

实验监督脚本记录的是本轮绝对路径和个人容器名，不能在已完成目录直接重跑：已有完成标记可能被复用，部分目录明确拒绝重复创建。下一轮需创建新结果目录、同步选定脚本并更新目录配置，再检查空闲卡后启动。不要覆盖旧结果，也不要停止别人的容器。

## 容器重建与补丁自动化

同一个容器的重启通常保留它的可写层；本项目使用 `--rm` 一次性容器，停止后容器会被删除，下次新建容器从旧镜像重新开始，所以需要重新应用 vLLM 补丁。补丁脚本和结果保存在宿主机及 Git 中，不随容器删除。

现有 `results/native2d_20261011/run_validation.py` 的 `run_stage()` 已自动完成：启动新容器 → 校验两份原始源码哈希并应用补丁 → 保存 diff/manifest → 设置 `VLLM_FL_NATIVE2D_PROBE=1` 启动服务 → 评测 → 清理个人容器。每个精度/吞吐阶段都重复这一自动过程，不需要人工编辑 vLLM 文件。源码不匹配时立即停止，不继续跑评测。

`environment/run_tianshu_container.py` 本身只启动原版环境，不自动打补丁，也不启用 Native 2D；同卡基线使用这一方式。单独手动启动容器后要测试优化，应显式运行已提交的补丁脚本并以实验开关启动服务，不能把普通容器当作已经优化的环境。归档中的监督脚本不能在旧结果目录直接再次执行，下一轮应先使用新结果目录配置。

当前 Dockerfile 未把 Native 2D 补丁烘焙进镜像，也未构建新镜像，符合暂时沿用旧镜像的约定。方案稳定后再维护包含固定源码与补丁的 Dockerfile、构建个人镜像，届时新容器可直接带上优化。

## Git 工作约定

源码及实验脚本在本地修改、检查、提交到独立实验分支。推送个人 fork 后，服务器个人仓库拉取指定分支和提交；每次启动记录插件提交、镜像摘要、补丁哈希及输出目录。容器内的安装文件由已提交补丁生成。

当前归档分支为 `perf/iluvatar-native2d-experiments`。原混合方案、诊断、原生 KV 布局和阈值路由分支保留；布局与阈值分支未上机。补丁与结果通过这个实验分支发布到个人 fork；是否发布成功以远程分支提交核验为准。当前开发分支已同步到本地、个人 fork 和服务器个人仓库，服务器工作区干净；旧服务器历史及完整实验结果已备份并保留。同步校验及后续工作约定见 `GIT_STATUS.md`。
